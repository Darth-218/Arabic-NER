## 1. Method in plain terms

Named-entity recognition is a labelling task: for each word in an Arabic
sentence we choose a **BIO tag** — `B-PER`/`I-PER` for a person, `B-ORG`/`I-ORG`
for an organization, `B-LOC`/`I-LOC` for a place, and `O` for everything else.
`B` starts an entity, `I` continues one, `O` means "not an entity".

AraBERT is a **pretrained** BERT-base model (~136M parameters) trained by
AUB's MindLab on a large Arabic news/MSA corpus. It already knows Arabic
morphology, spelling variants and sentence structure before it ever sees
WikiANN. We attach a token-classification head (one output per BIO label) and
fine-tune the whole network on the 20,000 training sentences, so the model
learns *which words are names* while keeping its Arabic language knowledge.

## 2. Why this approach, and how it differs from the team

| Member | Model | What makes it different |
| :--- | :--- | :--- |
| M1 | CRF | Classical ML: hand-designed features, no pretrained language knowledge. |
| M2 | mBERT | One model for 100+ languages; broad but not Arabic-specialized. |
| **M3 (this work)** | **AraBERT** | Arabic-specific pretrained model, mainly **news/MSA** text (the closest domain to Wikipedia among the Arabic models). |
| M4 | MARBERT | Arabic-specific and **dialect-aware** (tweets). |

The comparison answers a concrete question: does Arabic specialization help on
a Wikipedia-style benchmark, and does the **domain** of the pretraining text
(news vs tweets) matter? AraBERT's news/MSA domain matches WikiANN's formal
register more closely, while MARBERT brings dialect robustness.

## 3. Data and preprocessing

- Data comes only from `data/load_data.py::load_arabic_wikiann()`
  (20k train / 10k validation / 10k test), never from a private copy.
- Labels come only from `src/common/config.py`; `train.py`, `hparam_search.py`
  and `predict.py` import the canonical schema.
- Arabic normalization (diacritics, tatweel, alef and ya variants) is enabled in
  `configs/arabert.yaml` and applied to **model input only**. Prediction JSONL
  echoes the original WikiANN surface forms (ROADMAP §2.4), so predictions are
  directly comparable to gold tokens.
- Subwords: only the first subword of each word carries the word's label; the
  rest are `-100` and ignored by the loss (`label_all_subwords: false`). At
  prediction time the first subword's decision maps back to exactly one tag per
  original word, which is what `src/evaluate.py` requires.
- `max_len` = 128 with the fast tokenizer. A truncation audit found **0/10,000
  test** and **0/10,000 validation** sentences over 128 sub-tokens (longest
  encodings 84 and 107), so word coverage is 100% and truncation does not
  deflate the score.

## 4. Training setup and hyperparameter selection

- Checkpoint: `aubmindlab/bert-base-arabertv02`, BERT-base architecture.
- Hugging Face `Trainer`: 4 epochs, learning rate 5e-5, batch size 8 with
  gradient accumulation 2 (effective batch 16), warmup ratio 0.1, weight decay
  0.01, seed 42, bf16 autocast, gradient checkpointing to fit a 4 GB RTX 3050.
- Hyperparameters were selected **on validation only** with a staged 5-trial
  search (`src/approach_3_arabert/hparam_search.py`). The test split was not
  touched until the final evaluation.

| lr | epochs | max_len | Validation F1 |
| ---: | ---: | ---: | ---: |
| 2e-5 | 3 | 128 | 0.9097 |
| 3e-5 | 3 | 128 | 0.9118 |
| 5e-5 | 3 | 128 | 0.9144 |
| **5e-5** | **4** | **128** | **0.9197** |
| 5e-5 | 4 | 96 | 0.9180 |

Selected: **lr 5e-5, 4 epochs, `max_len` 128**. Lower learning rates trail
5e-5, a fourth epoch adds ~0.005 F1, and shortening the context loses a little
accuracy with no speed benefit worth taking. `batch_size` stayed at 8 for VRAM
reasons. The winning config was then retrained once as the deliverable; the retrain
reached validation F1 0.9200, so the reported model is not the search run
itself. (The trainer's own bf16 evaluation printed 0.9202; the committed
metrics file, produced by fp32 inference through `predict.py` and
`evaluate.py`, is the canonical 0.9200.)

## 6. Error analysis

From `reports/analysis/arabert_error_analysis.md` (counts in
`reports/analysis/arabert_errors_summary.json`). On the test split there are
11,259 gold entity spans; 10,349 are predicted exactly. The 910 errors break
down as:

| Error type | Spans |
| :--- | ---: |
| Right boundary, wrong type | 399 |
| Wrong boundary, same type | 273 |
| Wrong boundary and type | 88 |
| Missed entirely | 150 |
| Unmatched predicted spans (spurious) | 272 |

**53.5% of the missed gold spans carry the wrong label** (399 of them with the
boundary exactly right, 88 also wrong on the boundary), and LOC↔ORG alone
accounts for 250 spans. ORG is the weakest class (0.8843),
driven by long, transliterated and place-like organization names, e.g.:

```
منع تفكك الاتحاد السوفيتي هذه الأهداف من أن تتحقق .
gold: O B-ORG I-ORG I-ORG O O O O O O
pred: O O I-LOC I-LOC O O O O O O
```

Boundary errors are mostly spans absorbing the following common noun:

```
وهو الأبن غير الشرعي ألكسندر دوما الأب .
gold: O O O O B-PER I-PER O O
pred: O O O O B-PER I-PER I-PER O
```

Some "errors" are annotation noise rather than model failures — WikiANN marks
`Twitter` as ORG in `Kang So-ra on Twitter` but not `Kang So-ra` as PER, and the
model makes the opposite (reasonable) choice. This caps how much a perfect
model could score on such sentences. Since most remaining errors are type
errors, a type-aware second pass (for example CRF transitions over AraBERT
logits) is the most promising next step; more boundary data is not.

## 7. Reproducibility

```bash
pip install -r requirements-gpu.txt        # torch, transformers, datasets, seqeval
python src/approach_3_arabert/train.py --config configs/arabert.yaml
python src/approach_3_arabert/predict.py --model_dir results/models/arabert \
  --split test --out results/predictions/arabert_test.jsonl
python src/evaluate.py --model arabert --split test --config configs/arabert.yaml

# optional: re-run the validation-selected search (5 trials, ~67 min)
python src/approach_3_arabert/hparam_search.py
```

The retrain takes ~16 minutes on a 4 GB RTX 3050 (5,000 optimizer steps).
Predicting the test split takes under a minute; evaluation is CPU-only.
